# jc-import-file-maker の位置づけと今後の方向性

作成日: 2026-07-05（JST）

## 概要

`jc-import-file-maker` は、JAIRO Cloud（WEKO3）へのメタデータ登録に先立ち、入力担当者が DOI や外部 API から取得した情報を確認して補完し、デフォルトアイテムタイプ向けの TSV を作成する支援ツールである。

本ツールは、NII 公式の OA Assist を置き換えるものではない。
OA Assist が業務フロー管理、SWORD 連携、登録状況管理を担うのに対し、本ツールはメタデータの補完、確認、編集を支援する。

## 出発点

本ツールの出発点は、WEKO3 の入力 UI だけでは、JPCOAR スキーマに沿った判断・補完・確認を行う負荷が入力担当者に大きくかかる、という問題意識にある。

JPCOAR の項目は、単に値を入力すればよいものではなく、以下のような判断を伴う。

- どの識別子をどのフィールドに入れるべきか
- 著者名・所属・識別子をどの粒度で整理するか
- DOI 登録要件や JPCOAR スキーマ上の必須度をどう確認するか
- OA 状態、出版タイプ、アクセス権、エンバーゴをどう判断するか
- 助成情報や関連情報をどのように補完するか
- JaLC / Crossref / DataCite など、DOI 登録機関ごとの差異をどう扱うか

このため、JAIRO Cloud の入力 UI を操作する前に、判断材料を集めて入力候補を整える処理が必要になる。
本ツールはこの前処理を担う。

## OA Assist との関係

OA Assist は、NII 公式の登録支援およびワークフロー管理ツールである。
公式案内では、機関に所属する研究者の学術雑誌論文情報を Lens や J-STAGE などの外部データベースから収集し、一覧で管理する機能として説明されている。

OA Assist では、以下の作業を一連の流れとして扱う。

- 機関に関係する論文の把握・抽出
- 出版社ポリシーや査読の有無等の確認
- 著者への本文提供依頼
- JAIRO Cloud への論文情報の連携
- 連携後の登録状況の管理

また、OA Assist では DOI からのメタデータ取得と、SWORD API による JAIRO Cloud 登録の流れが実現されている。

一方で、OA Assist の利用には、JAIRO Cloud 側の Developer Application 登録、Client ID / Client Secret / Redirect URI の設定、OA Assist 側の機関設定、SWORD API 設定、JSON-LD マッピング設定などが必要であり、初心者向けというよりは、機関リポジトリ担当者・システム管理者・運用設計者向けの業務マニュアルとしての性格が強い。

## OA Assist で手が届きにくい部分

OA Assist は公式の業務基盤として強力である一方、メタデータの細部補完については、入力担当者による確認・編集が必要になりやすい部分がある。

たとえば、OA Assist は Crossref DOI の記述を基本的にそのまま利用するため、著者所属情報は Crossref 側の記述に依存する。
Crossref の所属情報には ROR などの所属機関識別子が含まれない場合があり、機関名の正規化や識別子の補完は担当者の作業として残る。

本ツールでは、このような細部を補うために、以下のような機能を重視している。

- OpenAlex / ROR による作成者所属の補完
- ROR 誤同定の疑いがある場合の要確認表示
- ORCID 補完
- OPF による OA ポリシー参照
- KAKEN / JGN / CiNii による助成情報補完
- JaLC DOI 対応
- DataCite DOI 対応
- DOI 登録要件や JPCOAR 項目の確認支援
- デフォルトアイテムタイプ向け TSV 生成

したがって、本ツールは OA Assist と競合するものではなく、OA Assist や JAIRO Cloud 標準機能だけでは補いきれないメタデータ整備作業を、担当者が手元で補完・確認するための補助工具である。

## 現在の実用範囲

本ツールは、デフォルトアイテムタイプを前提とするメタデータの取得、編集、TSV 生成に利用できる。

生成した TSV は、デフォルトアイテムタイプを使う少数の JAIRO Cloud 実機で取り込めることを確認している。
ただし、確認例は5件未満であり、デフォルトアイテムタイプ全般について検証済みと評価できる段階ではない。
各機関がカスタマイズしたアイテムタイプも一律には扱えない。

当面は、デフォルトアイテムタイプでの信頼性向上、運用改善、レビュー支援を主対象とする。

## カスタムアイテムタイプ対応の限界

JAIRO Cloud のアイテムタイプは、デフォルトアイテムタイプを除くと各実機でのカスタマイズが多く、どのようなパターンが存在するかを事前に網羅的に把握することは難しい。

そのため、カスタムアイテムタイプへ一律対応する汎用マッピングを先回りして実装するのは、実装コストの見積もりが困難で、費用対効果も読みにくい。

対応する場合は、各実機からエクスポートした TSV テンプレートを読み込み、そのテンプレートに合わせて出力列、プレフィックス、サブフィールド構造を解釈する。
ただし、テンプレート差異を吸収する範囲によって実装コストは大きく変わる。

したがって、当面はデフォルトアイテムタイプを主対象とし、カスタムアイテムタイプは個別要望・実サンプルに基づいて段階的に対応するのが妥当である。

## サーバサイド化を検討する場合

将来的にサーバサイド化する場合でも、いきなり SWORD による自動投入を主目的にするより、まずは担当者向けレビュー支援基盤として考えるのが現実的である。

想定される環境には、以下のような段階がある。

### GitHub Actions 定期実行

OpenAlex から定期的に候補 DOI を取得し、CSV / JSON / TSV の候補リストを生成する軽量な構成である。

向いている用途は、OpenAlex 定期ハーベスト、DOI 候補リスト作成、既登録チェックの簡易バッチ、担当者向けレポート生成である。

一方で、対話 UI や永続的な状態管理には向かない。

### Node.js CLI

既存のマッピングロジックを UI から分離し、コマンドラインで DOI リストから TSV を生成できるようにする構成である。

ブラウザ UI から切り離して、同じ TSV を安定して生成できるかを確認する段階として有効である。

### Node.js Web アプリ

Express / Fastify / Next.js API Routes などで、既存 JS ロジックを移植・共通ライブラリ化する構成である。

処理済み、除外済み、要確認、登録候補などの状態管理、担当者向けレビュー画面、TSV 生成、将来的な承認ワークフローに向いている。

DB としては SQLite または PostgreSQL が候補になる。

### 機関内サーバ / VPS

大学・研究機関内で運用する場合には、Docker Compose で Node.js + PostgreSQL + 定期実行処理を組む構成が現実的である。

機関ごとの設定を固定し、API キーやリポジトリ接続情報を外部 SaaS に置きたくない場合に向いている。

一方で、サーバ管理、バックアップ、セキュリティ更新、利用者認証の設計が必要になる。

### クラウド小規模構成

Render / Fly.io / Railway / AWS App Runner / Google Cloud Run / Azure App Service などに載せる方式も考えられる。

複数機関や複数担当者で使う場合、または Web UI を継続して提供する場合に向く。
ただし、機関データ、API キー、認証、学内ポリシーとの適合性を確認する必要がある。

## サーバサイド化で優先すべき領域

OA Assist がすでに DOI からのメタデータ取得と SWORD による JAIRO Cloud 登録を実現していることを踏まえると、本ツールが独自にサーバサイド化する場合の優先領域は「投入エンジン」ではなく、「担当者向けレビュー支援」である。

特に価値が出るのは以下である。

- OpenAlex / ROR による所属補完と要確認表示
- DOI 候補リストの収集
- 既登録確認
- 除外管理
- OA Assist で拾えない候補の発見
- Crossref 記述そのままだと不足する識別子・助成情報・OA ポリシーの補完
- 入力担当者がレビューしやすい比較画面や差分表示
- デフォルトアイテムタイプ向け TSV 生成の安定化

SWORD v3 などによる自動投入は、レビュー・承認・ログ・責任分界が固まってから検討するのが安全である。

## 著者への本文提供依頼

OA Assist には、著者への本文提供依頼メールとステータス管理の機能がある。
本ツールでも、簡易的な本文提供依頼は支援できる。

たとえば、以下のような機能であれば比較的軽量に実装できる。

- 著者メールアドレスの手入力
- タイトル、DOI、掲載誌、希望する版を差し込んだ `mailto:` リンク生成
- OPF / OpenAlex から推定される投稿可能版を文面に反映
- 本文提供依頼テンプレートの設定

ただし、送信履歴管理、進捗管理、メールテンプレート管理、ステータス管理まで含めると OA Assist の中核領域に近づくため、本ツールで行う場合は「簡易 mailto リンク生成」程度に留めるのが現実的である。

優先順位は高くないが、担当者支援という本ツールの方向性には合っている。

## jpcoarschema-helper との連携

将来的には、JPCOAR スキーマ入力判断を支援する `jpcoarschema-helper` と連携することで、より一貫した入力支援が可能になる。

`jpcoarschema-helper` は、入力フローチャートと項目判断支援を担う。
一方、`jc-import-file-maker` は DOI や外部 API からメタデータを取得して補完し、TSV 生成と編集 UI を提供する。

両者を組み合わせることで、以下のような役割分担が考えられる。

```text
1. 判断支援
   jpcoarschema-helper
   - 入力フローチャート
   - JPCOAR項目の判断支援
   - 必須/条件付必須/推奨入力の案内

2. 取得・補完支援
   jc-import-file-maker
   - DOIからメタデータ取得
   - ROR/ORCID/助成情報/OAポリシー補完
   - 担当者が確認しやすい編集UI
   - デフォルトアイテムタイプ向けTSV生成

3. 公式運用・登録
   OA Assist / JAIRO Cloud
   - 候補管理
   - 本文提供依頼
   - SWORD連携
   - 登録状況管理
```

本プロジェクトで複数の仕様を照合する必要があった箇所は、入力担当者も判断を誤りやすい。
そこで得た条件や例外を `jpcoarschema-helper` の説明、分岐、注意事項に反映すれば、両ツールで判断基準を共有できる。

## 今後の方向性

今後の方向性としては、カスタムアイテムタイプへの汎用対応や、SWORD による完全自動投入を急ぐよりも、以下を優先するのが現実的である。

- デフォルトアイテムタイプでの信頼性向上
- TSV 出力の安定化
- 入力担当者が確認しやすいレビュー支援
- ROR / ORCID / 助成情報 / OA ポリシー補完の精度向上
- OpenAlex 等を使った候補発見と重複確認
- OA Assist では拾いきれない・整えきれない細部の補完
- `jpcoarschema-helper` との連携による判断支援

本ツールは、**OA Assist や JAIRO Cloud の公式フローの前後で、入力担当者の判断と補完作業を支える実務支援ツール**として開発を続ける。

### 確認できた事項

- OpenAlex と ROR による補完、要確認表示（#186）、ORCID 補完、OPF、KAKEN、JGN、CiNii による助成情報補完、JaLC、DataCite（#208、#212、#214）、TSV 生成はコードに実装されている。
- OA Assist に関する記述（NII 公式、SWORD v3 連携、メタデータ入力後の JAIRO Cloud 登録）は、NII RCOS の公式情報と一致する。
- `jpcoarschema-helper` の役割（入力フローチャートと項目判断支援）は、姉妹リポジトリの README と一致する。
- `jpcoarschema-helper` は、名前が似ている YAML から XML への変換ツール `jpcoar-schema-helper` とは別のプロジェクトである。
- 本文提供を依頼する `mailto:` リンクは未実装であり、将来の低優先機能として扱っている。

### インポートの検証状態

少数の実機で取り込みに成功した一方、`README.md` と `current_review_2026-07-05.md` はインポートを未検証としている。
実機確認は5件未満であり、「デフォルトアイテムタイプ全般で検証済み」とは評価できない。
本文も、少数例での成功と検証完了を区別する表現に改めた。

### サーバー側で実行する構成の実現可能性

- **GitHub Actions の定期実行**：Phase 3 の OpenAlex パイプライン（#157、手動運用版）を定期実行へ拡張する構成であり、既存実装からの変更範囲が小さい。
- **Node.js CLI**：#208 と #214 の検証では、マッピングロジックが Node.js 上で単体動作している。  
  CLI 化に伴ってロジックを UI から分離すれば、標準版と拡張版の二重保守も減らせる可能性がある。
- **Node.js Web アプリ以降**：認証、運用主体、API キー管理が必要になり、CLI より運用コストが増える。  
  当面の実装対象には含めない。
- **SWORD による自動投入**：OA Assist と機能が重複するうえ、レビュー、承認、ログ、責任分界の設計が必要になる。  
  これらの運用要件が定まるまで実装対象には含めない。

### レビュー結果

OA Assist の代替ではなく、その前後でメタデータ整備を補助するという位置づけは、実装済みの機能と一致する。
デフォルトアイテムタイプでの信頼性向上を優先し、カスタムアイテムタイプへの汎用対応と SWORD 自動投入を後回しにする順序も、現時点の検証範囲に合っている。

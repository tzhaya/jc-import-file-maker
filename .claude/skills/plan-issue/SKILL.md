# Issue実装計画

`gh` が見つからない場合はフルパス `"/c/Program Files/GitHub CLI/gh.exe"` を使う。

## 段階的に読む

最初にタイトル、本文、ラベルだけを取得する。

```powershell
gh issue view <number> --json number,title,body,labels,url
```

追加情報が必要な場合だけ、コメントのID、作成者、日時、先頭見出し、文字数を一覧化する。
計画に関係するコメントだけ本文を取得し、長いコメントを全件読み込まない。

## 暫定リスクを提案する

- low: 定型的な小規模変更で、動作、互換性、外部API、共有コードへ影響しない。
- medium: 複数ファイルの動作変更、標準版と拡張版の同期、確認済みAPIの利用。
- high: 未確認の外部仕様、永続形式、権限、非同期競合、実行環境依存、大規模構造変更。

lowで変更と受入条件が明確ならPlan不要と提案する。
分類は暫定値であり、人間の確認対象とする。

永続形式、権限、未確認API、非同期競合、Service Worker、スクリプトの重複読み込み、グローバル名前空間、不可逆な変換が判明したらhigh候補として再評価する。
該当しただけで計画crossを要求せず、手戻りが大きければ計画cross、実コードで判断できるならPR crossを選ぶ。

## 調査して計画を書く

関連ファイル、関数、既存テスト、同期先、実行環境を調べる。
中・高リスクで範囲が不明な場合だけExploreエージェントを使う。

計画には、概要、対象範囲と対象外、暫定リスクと根拠、影響箇所、10項目以内の手順、Issue固有の受入条件、テスト、未確認事項、格上げ条件を含める。
設計判断がある場合だけ代替案を書く。

## 投稿する

一時ファイルに本文を書き、`gh issue comment <number> --body-file <path>`で投稿する。
`risk:*`と`scope:*`はラベル、受入条件とテストはIssue本文または構造化コメントへ残す。
分類変更は理由と追加工程だけを短く記録する。

分類履歴を毎回儀式的に記録しない。
同種の見逃しが2回発生した場合に、分類基準またはテストへ恒久反映する。
